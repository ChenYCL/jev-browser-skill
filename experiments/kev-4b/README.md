# Kev on the 20-item benchmark (Kev control row)

EXPERIMENTAL — not part of the jev-browser skill.

Grades a **Kev** server (`jaredpalmer/kev` → `/v1/systemone`) on the *same* 20 construction-graded
items and the *same* real captured fixture step the local GGUF candidates were measured on, so a
Kev checkpoint can be compared apples-to-apples with them.

- Items: reused verbatim from `../gguf-provider/eval/items.mjs` (read-only import — nothing under
  `eval/` is touched). 15 browser + 5 passage yes/no, ground truth known by construction.
- Fixture step: `../gguf-provider/fixtures/judge-state.json` + `judge-questions.json`
  (5 questions; the state is byte-identical to the ddg item fixture).
- Request path: the skill's own client, `skills/jev-browser/lib/typesafe.mjs` (`TypeSafeClient`),
  i.e. exactly the path hosted Jev used — base URL pointed at Kev, answers consumed natively.

## Environment

|---|---|

when a run id is not resolvable — see traps 1 and 7 in `docs/local-kev-bringup.md`.

## Launcher — `skills/jev-browser/bin/jev-kev.mjs`

The one-command path, and the one to prefer over the manual steps below. It fetches and verifies the
checkpoint plus its base, starts the server, and prints the skill's env line last (everything else
goes to stderr, so the line can be eval'd).

```bash
node skills/jev-browser/bin/jev-kev.mjs                       # published 8192 cap
node skills/jev-browser/bin/jev-kev.mjs --row-limit 16384      # needs --patch-row-limit first
node skills/jev-browser/bin/jev-kev.mjs --verify-only          # re-hash 29 files, download nothing
node skills/jev-browser/bin/jev-kev.mjs --list-files           # the pinned manifest
node skills/jev-browser/bin/jev-kev.mjs --patch-row-limit      # optional; prints diff + revert
node skills/jev-browser/bin/jev-kev.mjs --unpatch-row-limit
```

How it behaves (all exercised in the run log below):

- **Pinned manifest, verified per file.** The 29 files of `jaredpalmer/kev-4b@485ace87` (16) and
  `Qwen/Qwen3.5-4B-Base@1001bb4d` (13) are embedded in the launcher with size + sha256 (LFS blobs) or
  git-blob sha1 (small files), generated by `make-manifest.mjs` from the Hub tree metadata. Every file
  on disk is re-hashed before it is trusted; a file that fails is deleted and the next source is tried,
  and if every source fails the launcher exits **3** rather than caching the bytes.
- **Sources, fastest first:** `modelscope → hf → hf-mirror`, overridable with `--source`/`--sources`.
  A source that serves bytes failing verification is demoted for the rest of the run — which is how
  ModelScope's different `.gitattributes` is caught, since the base's small files must come from HF.
  Each file logs which source it came from and its MB/s; a stall (no bytes for 120 s) moves to the
  next source.
- **Resume:** partials live at `blobs/<hash>.incomplete` and are resumed with `Range`; a verified file
  is never re-downloaded.
- **Cache layout:** `blobs/`, `refs/main`, `trees/<commit>.json`, `snapshots/<commit>/<name>` symlinks —
  what `resolve_run` → `snapshot_download` needs, so the server runs with `HF_HUB_OFFLINE=1`.
- **Fails loudly, never silently:** a missing checkout or venv prints the exact `git clone` /
  `uv sync --extra serve` command and exits 2 (before the 9.5 GB verification, not after); a run other
  than the pinned one exits 2; a server already on the port is reused when it serves the same
  checkpoint and reported as a conflict otherwise; `--row-limit` without the patch exits 2.
- **The patch is explicit.** `--patch-row-limit` prints the unified diff and the revert command and
  leaves the defaults at 8192. On a clone where `kev/model.py` is not the released line, it refuses.

**Prerequisites for the 4B row** (checked on disk, 2026-09-24): the pointer head and LoRA are already
fetched — snapshot `485ace87…`, `adapter_model.safetensors` sha256 `9797de69…df2b` (128 MB, r=16,
alpha=32), plus `head.pt`, tokenizer and `provenance.json`. The one missing piece is the **base** the
checkpoint itself declares (`provenance.json → config.base`): `Qwen/Qwen3.5-4B-Base`
(rev `1001bb4d…`, 9.34 GB) — not in the HF cache yet, and `kev.serve --run jaredpalmer/kev-4b` fails
at load without it. Once it is cached, serving needs no network. Expected card, from the
checkpoint's own `head.pt`: base `Qwen/Qwen3.5-4B-Base`, `lora=16`, `head.pt["temperature"]`
`2.1435` (0.8B: `2.4061`; AGENTS.md lists 9B 2.30 / 4B 2.14 / 0.8B 2.41). Both read off the
checkpoints with `torch.load`, and that is the field that is served: `Checkpoint.load` assigns it
(`kev/checkpoint.py:172 m.head.temperature = meta.temperature`) and `/v1/models` reports it
(`kev/serve.py:155`). **Not a conflict:** `result.json` carries `2.3784`, which is the *pre-delta*
trial's temperature — the delta run refit it and `head.pt` holds the refit, so the 4B card will read
`2.1435`. The runner prints the served field at preflight, so the row is self-documenting.

**It cannot silently score something else.** `--run` is not decoration: before any request is
scored, the runner reads `GET /v1/models` and refuses to run (exit 2) unless the *served* checkpoint
equals `--run`. Two verified failure paths:

```
$ node experiments/kev-4b/run.mjs --run jaredpalmer/kev-4b          # 0.8B on the port
✖ served checkpoint is "jaredpalmer/kev-0.8b", but --run asked for "jaredpalmer/kev-4b".
  …serve the requested checkpoint first:  … -m kev.serve --run jaredpalmer/kev-4b --port 8008
EXIT=2

$ node experiments/kev-4b/run.mjs --base-url http://127.0.0.1:8012  # nothing listening
✖ Kev server not reachable at http://127.0.0.1:8012 (fetch failed). …
EXIT=2
```

A `kev-4b` checkpoint that is not on disk produces the run-id fallback (`runs/smoke`) **or** a
download attempt at whatever the WAN gives — either way the preflight stops the run loudly instead of
scoring the wrong model.

### Options

```
--base-url <url>     default http://127.0.0.1:8008
--model <name>       request/alias name                 default kev-latest
--run <hub-id>       checkpoint that MUST be served     default jaredpalmer/kev-0.8b
--label <slug>       result slug                        default: last path segment of --run
--out <dir>          result directory                   default results
--timeout <seconds>  per-call bound                     default 60
--set <all|browser|noul>          --no-fixture          --json
--only <id[,id]>     run just these items (the fixture step still runs)
```

## Output

```
results/
  raw/<label>/<item>.json      one file per item: request descriptor, untouched server answers,
                               normalized answer, probabilities, the degeneracy analysis, timing
  eval-<label>.json            all rows + summary (accuracy slices, Σp, near-uniform, noul separation)
  fixture-step-<label>.json    the same real captured step (packed, plus a per-question fallback)
```

Per item the runner records the brief's list: latency (`ms` wall and the server's own `latency_ms`),
the returned probabilities, whether they sum conventionally (`p_sum`, tolerance 1e-3), and the
degeneracy signature — `entropy_norm` (normalized Shannon entropy of the answer; ≥ 0.95 = near-uniform),
`margin`/`coinflip_margin` (top1 − top2 ≤ 0.05 = almost a coin toss), `choice_is_argmax`
(whether the reported `choice` matches its own probability map), and for `noul` `dev_from_half` /
`near_half` / `pinned_high`.

### Two structural refusals (not wrong answers — unanswerable)

`ddg-click-target-aapl` and the fixture step's `click_target` both return **HTTP 422**:

```
branch too long: 4700 tokens with a 6407-token state (row limit 8192)
```

`kev/model.py:15` — `SERVE_MAX_STATE, SERVE_MAX_BRANCH = 8192, 8192`; the row limit is
`state + one branch ≤ 8192` and is **not** env-configurable. The GGUF side hit the identical wall
(11,748 tokens on the same fixture) and fixed it with `llama.cpp -c 16384`; Kev has no equivalent
knob, so the 55/100-candidate `click_target` questions on a ~6.4k-token real state are
**unanswerable as served**. The fixture step therefore falls back to one question per pass, which
still yields the four short-branch questions. See *Row limit* below for the source check, the local
evaluation patch that makes the limit settable, and what the two refused items answer once it is
raised (short version: they answer, and the answers are still coin tosses).

### Same failure mode as the entropy tests, on the graded items

- **noul splits by state length, it is not globally pinned.** Short passages: 5/5, extreme
  (0.0070 / 0.1312 vs 0.9816 / 0.9859). Browser states: inverted and at chance —
  `goal_done` = **0.6952** on the fixture state (a false success; the GGUF 4B reads **0.006** on the
  identical state), and both `submit_after_type` items sit at **0.4594 / 0.4627**, i.e. ±0.04 of a
  coin flip — the one that scores "correct" does so because 0.4627 lands under the 0.5 threshold.
- **Choice distributions flatten on the long element lists.** `action` 0.4984/0.2385/0.1625 and
  `blocker` 0.4589/0.2400/0.1767; the 4-level `progress` score is near-uniform (H_norm 0.973,
  0.30 vs 0.30 for the top two levels) and only scores because the ±0.5 window rounds 1.749 to 2.

### Verdict

Kev 0.8B's 14/20 is **not** a number worth averaging into any shipping decision:

- It beats the GGUF 0.8B (10/20) and the always-first-option baseline (11/20) but is *wholly carried
  by the 5 short passages* (5/5) — which the GGUF 4B also nearly aces and which no browser decision
  depends on. Strip the passages and it is **9/14 = 0.64 on browser items vs 12/15 = 0.80 for the
  GGUF 4B**.
- The two question types a controller actually needs first (`goal_done`, `click_target`) are its
  worst: `goal_done` 0/1 (false success at 0.6952), `click_target` 1/2 with the other *unanswerable*.
- The two items that passed at ~0.46 (`submit_after_type`) would flip on any threshold change.

**Which types it did get right:** `blocker` (2/2, incl. the fixture state), `type_target` (2/3),
`wiki-progress` (by rounding), the short-passage `answer` nouls (5/5), and one `action` — i.e.
short-state, few-option, non-`goal_done` judgments. That is the same "short-state auxiliary only"
verdict `docs/local-kev-bringup.md` reached from entropy/pick tests, now reproduced on the graded
items.

### Memory — the real constraint

| | @8192 | @16384 |
| --- | --- | --- |
| footprint, fresh idle → after one request | 18 GB → 19 GB | 18 GB → 19 GB |
| RSS peak during the full 20-item run | 12.2 GiB | 18.6 GiB |
| footprint after the full run (incl. the 12k-token packed step) | — | **36 GB, entirely `IOAccelerator` (GPU)** |
| swap | unchanged (16.2 GB used) | driven 16.7 → **28.3 GB used of 28.7 GB total (416 MB free)** |

`ps -o rss=` under-reports this process badly — MLX's buffers are evictable, so RSS fell to 174 MiB
while idle — hence `footprint -p <pid>` is the number to trust. The raised limit costs nothing at
rest (18–19 GB either way, identical to the 8192 server); the 36 GB appears under the real workload,
and on this 48 GB machine that means heavy swap. Nothing failed or stalled (no request timed out) and
free memory recovered to 52–54% once the server stopped.

### Verdict

Kev 4B @16384 is **the best local backend measured on this set**: 19/20 = 0.95 vs the GGUF 4B's
16/20 = 0.80 (+3 items), and it **ties hosted Jev** on the total and on every slice. It beats hosted
Jev on exactly one question type (`click_target` 2/2 vs 1/2 — it picks the hand-labelled `e1`, the
only one of the five models that does) and loses on `submit_after_type` (1/2 vs 2/2). It does not
replace the GGUF path: it needs its own MLX runtime, ~36 GB of GPU footprint, the local row-limit
patch for the decisive item, and ~2.2 s mean / 12.2 s max per item. At the published limit it is
18/20 = 0.90 and cannot answer the `click_target` item at all.

## Threshold replay — does the loopback `goal_done` bar transfer to Kev?

The skill's loopback bar (`thresholds.goalDone` / `goalDoneFinal` = **0.174**, see
`skills/jev-browser/references/config.md`) was measured on the **GGUF readout** over the 15 runs of
`docs/local-backend-run-smoke.md` §9. Kev answers `goal_done` on a different scale, so the same 15
goals were replayed against Kev 4B with the same method and the same scoring.

```bash
# Kev 4B already up on :8008 (bin/jev-kev.mjs --row-limit 16384) and the fixture site on :3111
TYPESAFE_BASE_URL=http://127.0.0.1:8008 TYPESAFE_API_KEY=local \
  bash experiments/kev-4b/threshold-replay.sh /tmp/kev-threshold
node experiments/kev-4b/threshold-replay.mjs /tmp/kev-threshold
```

Method, unchanged from §9: one real `chrome --headless` run per goal with the controller's default
20 s per-request timeout; the reading is the journal's per-step `goal_done`; **ground truth is the page
that step saw** — `met` means the page itself already satisfied the goal, and a page that merely offers
a way to it is `not` (§9.1's rule, which is why a DuckDuckGo results page counts as not-met). The
labels are in `results/threshold-replay/labels.json` with the rule they follow written alongside; for
the fixture site they are checkable against `tests/fixtures/server.mjs` (the `/docs` secret only
appears after the reveal button is clicked, `/consent` is only satisfied once the dialog is gone, the
cart goal is the POSTed `Cart` page, the signed-in state is `/dashboard`, the contact goal is the
